# Hindsight Helped My Incident Agent Remember Being Wrong

The first diagnosis of a deployment failure is often plausible, specific, and wrong.

A Redis timeout, for example, can be the visible symptom of an exhausted database connection pool. The problem is not just making the first diagnosis better. It is making sure the next investigation remembers why that diagnosis was wrong.

I built OpsMemory around that idea: a previous, verified incident correction should become evidence during the next investigation. Hindsight is the part of the system that carries that experience from one incident to another.

## What I built

OpsMemory is a DevOps incident investigation service.

GitHub and GitLab webhooks enter a FastAPI backend, where provider-specific payloads are normalized into internal deployment and pipeline models. PostgreSQL stores the operational record: organizations, deployments, incidents, corrections, resolutions, and audit data. A React console gives engineers visibility into the investigation and a place to confirm or correct the diagnosis.

The investigation itself is a LangGraph workflow. It loads the incident, identifies its failure shape, recalls organizational memory, collects current evidence, checks for historical corrections, asks a Groq-backed reasoning provider for a diagnosis, and then pauses for human review.

A confirmed correction or resolution can become new memory.

That separation is important. PostgreSQL is the system of record for relational state. Hindsight is the organizational memory: the place where useful engineering experience can survive the end of an individual incident.

## The problem was not storing more context

The obvious implementation would have been to send the current logs, deployment diff, and symptoms to the model and ask for the root cause.

That is enough for a single investigation.

It is not enough for repeated incidents.

Incident response produces something that is more valuable than a transcript: an engineer eventually figures out where the initial reasoning was wrong. That correction is exactly the sort of thing I wanted the next investigation to inherit.

So instead of treating memory as a place to dump previous conversations, I gave the investigation a more explicit loop:

`current incident → fingerprint → memory recall → current evidence + prior correction → diagnosis → human review → outcome → retained learning`

The important part is what happens in the middle.

Memory does not replace the current logs. It changes the context in which those logs are interpreted.

## I needed a stable way to find the right memories

Before reasoning, the workflow generates a normalized incident fingerprint from information such as the service, environment, component, symptoms, and logs.

For a payment service, that might produce something like:

`PAYMENT_API_DB_POOL_PRODUCTION`

The fingerprint is deterministic rather than generated by the model. That gives the memory layer a stable operational handle for retrieval.

The implementation also records a more precise hash that includes the error category:

```python
norm_comp = cls.extract_component(
    norm_service, component, log_str, c_files
)

if not error_category:
    norm_cat = cls.extract_error_category(log_str, sym_str)
else:
    norm_cat = cls.normalize_string(error_category)

raw_fingerprint = f"{norm_service}_{norm_comp}_{norm_env}"

detail_hash = hashlib.sha256(
    f"{raw_fingerprint}_{norm_cat}".encode()
).hexdigest()[:10]

return {
    "fingerprint": raw_fingerprint,
    "hash": detail_hash,
    "service": norm_service,
    "environment": norm_env,
    "component": norm_comp,
    "category": norm_cat,
    "display": f"{raw_fingerprint} ({norm_cat})",
}
```

The useful distinction here is that the fingerprint identifies the shape of an incident; it does not decide its cause.

That matters because two incidents can look operationally similar while still requiring different reasoning.

I wanted memory retrieval to be deterministic enough to inspect and debug, without pretending that a fingerprint alone could solve the incident.

## The first time through, the system can still be wrong

Consider the payment service path used by the application.

A deployment goes out. The service starts returning 504s. The logs contain Redis connection timeout messages.

The workflow builds the incident fingerprint, retrieves any relevant memories, collects the current deployment evidence, and sends that context into the reasoning stage.

On the first occurrence, there may be no useful historical correction.

The model might reasonably conclude that Redis is unhealthy.

That diagnosis is allowed to be wrong.

The investigation is designed around the assumption that human review can produce information the initial reasoning did not have.

The memory retrieval node is intentionally simple:

```python
def recall_memory_node(state: OpsMemoryState) -> Dict[str, Any]:
    service = state.get("service")
    fingerprint = state.get("failure_fingerprint")

    query = (
        f"{service} {fingerprint} "
        "incident root cause correction"
    )

    tags = [
        service.lower(),
        fingerprint.lower(),
    ]

    memories = hindsight_service.recall(
        query=query,
        tags=tags,
        limit=5,
    )

    with Session(engine) as session:
        for m in memories:
            ref = MemoryReference(
                incident_id=state.get("incident_id"),
                memory_id=str(m.get("id")),
                memory_type=m.get(
                    "memory_type", "incident"
                ),
                relevance_score=0.95,
                source=m.get(
                    "source", "hindsight"
                ),
                content_snippet=m.get(
                    "contents", ""
                )[:300],
            )
            session.add(ref)

        session.commit()
```

The important thing is that the retrieved memories are not treated as the answer.

They become another input.

The engineer can then say, in effect, “Redis is only the symptom. The actual problem was PostgreSQL connection pool exhaustion.”

That correction is far more useful than the original incident transcript.

## I wanted the system to remember the correction

This is the write path that matters most to me.

When an engineer corrects the diagnosis, the system retains that correction in Hindsight along with the incident fingerprint and the verified root cause.

```python
retain_content = (
    f"Engineer Correction on {service} "
    f"[{fingerprint}]: "
    f"AI initially diagnosed "
    f"'{state.get('initial_diagnosis', {}).get('root_cause_hypothesis')}'. "
    f"Engineer corrected: '{correction_text}'. "
    f"Actual verified root cause: "
    f"'{actual_root_cause}'."
)

hindsight_service.retain(
    contents=retain_content,
    memory_type="human_correction",
    tags=[
        service.lower(),
        fingerprint.lower(),
        "human_correction",
    ],
    metadata={
        "incident_id": incident_id,
        "failure_fingerprint": fingerprint,
        "actual_root_cause": actual_root_cause,
        "is_corrected": True,
    },
)
```

I could have stored the entire conversation.

I deliberately cared more about the delta in understanding:

**What did we think was happening, what was actually happening, and what did an engineer verify?**

That is experience.

A transcript tells me what happened once. A correction tells me what I should remember the next time.

## The second incident is where memory becomes useful

The real test of persistent memory is not whether it can store something.

It is whether the stored information changes what happens later.

When another payment-service incident arrives with the same operational shape, the investigation follows the same path until memory retrieval.

Hindsight recalls the earlier experience.

The workflow then checks the recalled memories specifically for engineer corrections and other retained engineering knowledge:

```python
def check_historical_corrections_node(
    state: OpsMemoryState
) -> Dict[str, Any]:

    recalled = state.get(
        "recalled_memories", []
    )

    corrections_found = []

    for m in recalled:
        if (
            m.get("memory_type")
            in [
                "human_correction",
                "engineering_knowledge",
            ]
            or m.get("metadata", {}).get(
                "is_corrected"
            )
        ):
            corrections_found.append({
                "source": "hindsight",
                "contents": m.get("contents"),
                "actual_root_cause": (
                    m.get("metadata", {}).get(
                        "actual_root_cause",
                        m.get("contents"),
                    )
                ),
                "remediation": (
                    m.get("metadata", {}).get(
                        "remediation"
                    )
                ),
            })

    return {
        "historical_corrections":
            corrections_found
    }
```

The model still sees the current deployment diff and current logs.

That is important.

I do not want the system to learn a rule like:

> `PAYMENT_API_DB_POOL_PRODUCTION → always do X`

I want it to learn something closer to:

> “The last time we saw this shape, Redis looked suspicious, but an engineer verified that database pool exhaustion was the actual cause. Check whether the current evidence points to the same distinction.”

That is a much safer use of memory.

The historical correction changes the hypothesis space without replacing the investigation.

## Similar symptoms are not permission to replay a fix

This is where I think treating Hindsight as a simple cache would miss the harder engineering problem.

A relevant memory can still be wrong for the current situation.

The system therefore keeps human review between diagnosis and action. A recalled correction can influence what the agent recommends, but it does not automatically execute the previous remediation.

There is another distinction I wanted to preserve: a diagnosis is not the same thing as a successful resolution.

The system records resolution outcomes separately from memory, so an action that was recommended once does not automatically become “proven” just because it sounded reasonable.

Only an observed outcome can establish that the remediation actually worked.

The final learning step can then retain the incident-to-resolution relationship:

```python
def retain_learning_node(
    state: OpsMemoryState
) -> Dict[str, Any]:

    incident_code = state.get("incident_code")
    service = state.get("service")
    fp = state.get("failure_fingerprint")

    root_cause = (
        state.get("confirmed_root_cause")
        or state.get("initial_diagnosis", {})
            .get("root_cause_hypothesis", "Unknown")
    )

    action = state.get(
        "selected_action",
        "Rollback",
    )

    correction = (
        state.get("human_correction", {})
        .get("correction_text")
        if state.get("human_correction")
        else None
    )

    content = (
        f"Deployment Incident {incident_code} "
        f"for {service} "
        f"[Fingerprint: {fp}]. "
        f"Root cause was verified as: {root_cause}. "
        f"Effective remediation action: {action}."
    )

    hindsight_service.retain(
        contents=content,
        memory_type="engineering_knowledge",
        tags=[
            service.lower(),
            fp.lower(),
            "resolution_learning",
        ],
        metadata={
            "incident_code": incident_code,
            "service": service,
            "failure_fingerprint": fp,
            "root_cause": root_cause,
            "remediation": action,
            "has_human_correction":
                bool(correction),
        },
    )
```

The result is a feedback loop where the thing learned from one investigation can influence the next one.

That is much more interesting to me than simply giving the model more context.

## Three behaviors matter

The first encounter is intentionally unremarkable.

`payment-api` emits 504s and Redis timeout messages. The model proposes a Redis-related hypothesis. An engineer corrects it to PostgreSQL connection pool exhaustion. That correction is retained.

The second encounter is different.

The same service and incident shape appear again. Hindsight recalls the earlier correction. The reasoning stage now has historical evidence saying that the obvious Redis symptom previously hid a database problem.

The agent does not have to rediscover that mistake from scratch.

The third case is the one that prevents this from becoming a glorified replay engine.

Another service reports a timeout, but its current evidence and incident characteristics differ. A related historical memory may still be retrieved, but retrieval does not turn the old remediation into an automatic command.

The current incident still has to justify the current decision.

## What I would reuse from this design

**Store corrections, not just conversations.**

The most valuable memory from an incident was not that the incident happened. It was that an engineer discovered where the original reasoning was wrong.

**Give memory a stable retrieval handle.**

A deterministic incident fingerprint makes recall inspectable. When memory behaves unexpectedly, engineers need to be able to understand why a memory was retrieved.

**Keep historical memory separate from current evidence.**

Hindsight provides prior experience. Logs, diffs, and deployment state describe what is happening now. Those inputs should meet during reasoning, not collapse into one undifferentiated source of truth.

**Record outcomes independently from diagnoses.**

A plausible recommendation is still only a recommendation. The system needs actual resolution outcomes before it can treat an action as reliable historical evidence.

**Treat memory as a decision input, not an execution command.**

This is probably the most important lesson.

Persistent memory makes an agent more useful when it lets the system learn from previous reasoning and previous mistakes. It becomes much harder to trust when an old answer quietly turns into a permanent rule.

## Closing the loop

For the Hindsight integration itself, the underlying concepts are documented in the [Hindsight repository](https://github.com/vectorize-io/hindsight) and the [Hindsight documentation](https://hindsight.vectorize.io/). Vectorize also has a useful overview of [agent memory](https://vectorize.io/what-is-agent-memory).

The interesting result of this system is not that the agent suddenly knows the root cause.

It is that the investigation can remember being wrong.

A first incident produces a hypothesis. An engineer corrects it. The correction survives the end of the incident. When the misleading symptom appears again, that experience becomes part of the reasoning context.

That is the kind of memory I wanted: not an archive of everything the agent has seen, but a way to carry verified lessons forward.
